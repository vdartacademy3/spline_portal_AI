### Finding: DEFECTS 1 and 2 CONFIRMED
UPDATE and DELETE apply authorization as a queryset filter:
    qs = model.objects.all()
    if not _is_service(user): qs = qs.filter(policy.update_q/delete_q(user))
    qs = qs.filter(_collect_filters(...)); rows = list(qs)
When the policy excludes the target, `rows == []`, and the handler returns
`JsonResponse({}, status=204)` — byte-identical to a legitimate zero-row match.
The only explicit denial that existed was the row-level `check_ok` (patch), which
returns 401 and is bypassed entirely when `rows` is already empty. Net effect:
a caller without update/delete permission receives a success status for a
mutation that never happened.

Reproduced with mocks BEFORE any fix:
  - denied UPDATE returned 204 with no indication of denial
  - denied DELETE returned 204

### Correction applied (smallest safe fix)
Added `_deny_if_filtered_out(model, request, rows, is_service)` in rest.py and
called it in both `patch` and `delete` immediately after `rows = list(qs)`.
When a non-service caller resolves zero rows but the same request filters match
an existing row, it raises 403 / "permission denied for table" (42501).
Service role and genuine zero-row matches are unaffected (no extra query in the
success path; the probe only runs when `rows` is empty and the caller is not service).
